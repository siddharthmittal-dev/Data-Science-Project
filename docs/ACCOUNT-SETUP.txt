The following is historical setup information, not current instructions.

During the previous setup, the now-removed Create an account form was used.
Enter a name, email and a password of 12–128 characters, then choose a role.
One registered account is allowed for each role: Patient, Receptionist, Owner.
Owner is displayed as Owner; the existing API/database role remains admin.
Registration signs the new account in. Sign out before creating the next account.
Roles disappear from sign-up after registration. Duplicate role/email requests
are rejected by the database, including competing requests.
Sign-in uses email and password only; role is read from the stored account.

Passwords use individually salted scrypt hashes. Sessions last eight hours and
use HttpOnly, SameSite=Lax cookies. COOKIE_SECURE must be true when using HTTPS.
Successful authentication rotates the browser's current session token.
The former /api/auth/demo-login endpoint has been removed.

The migration retains existing users, appointments and patient libraries. Existing
unregistered fixture identities cannot sign in. New registrations create separate
identities and do not inherit someone else's patient records. Existing fixture
emails remain reserved by their existing records; register a different email.
The migration expires existing role-picker sessions, requiring sign-in again.
Do not rerun the database seed to apply this change: it clears application data.

Current account emails are patient@terra.test, receptionist@terra.test and
owner@terra.test. Their passwords are not included in the repository.
There is no email verification, password recovery, MFA or login rate limiting yet.
This requested first-registration role selection allows whoever first registers
to claim Owner or Receptionist. Register all three intended accounts before
sharing access. Role restrictions remain enforced after sign-in.
